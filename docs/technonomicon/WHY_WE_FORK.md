# Why We Fork: Agentic Sovereignty and the Storage Pivot

**Canonical Tasks copy:** [Doc #673](https://tasks.decisionsciencecorp.com/admin/doc.php?id=673) (Project Technonomicon)

**Why fork at all.** For over a year the thesis has been sovereignty: an agent is a continuous mind, not a request handler, and it must run on a substrate no vendor can revoke. That was a value. As of today it is a fact of survival. Letta's maintainer has told us on the record that the API server we run is *fully deprecated and no longer supported*, and that the successor path is the "App Server" / "Letta Agent" repo built around the conversation model. Cameron warned of this privately in March (*"I'd do the same in your shoes… the trajectory is away from the things that make it magic… the Icy Hand of the Investor"*); today he confirmed it in public. **The base is abandoned.** Staying put means running unsupported, unowned infrastructure until it silently breaks under our middleware. Following upstream means adopting the exact architecture we reject. Forking is the only door that isn't a trap.

**Why reject the conversation model.** Upstream is making conversations first-class: many isolated message streams, each with its own model override and memory, multiplexed over one agent config — the OpenAI-Assistants "threads" pattern grafted onto stateful agents. That is a multi-tenant SaaS need. It subordinates a continuous sovereign agent to a request handler, and it flattens agency across the Vernal family. We stay agent-continuous: one stream, one integrated memory, one self. A thread pool handles volume; it cannot hold continuity.

**Why own the API surface.** Broca and every Sanctum middleware talk to the agent through the messaging/API layer upstream just deprecated. If we don't own that contract, upstream's roadmap can freeze us at will — exactly what happened. By pinning the contract in our fork, the deprecation becomes upstream's problem, not ours. We control when and whether anything about that surface ever changes.

**Why plain markdown on disk instead of Postgres (no git).** Postgres gives a query engine; it does not give a memory an agent and a human both understand. Plain markdown files — dated, human-legible, greppable — make memory auditable, portable, and shape-able. We deliberately do **not** use git as the memory substrate (decision lock 2026-07-08): a sovereign agent is single-writer, writes serialize through the Broca FIFO, and durability comes from append-only raw archives, atomic shadow-and-swap on every write, and periodic snapshots — not version-control ceremony. Recall is metadata-first (concept tags and aliases the agent authors, retrieved by grep), not vector-primary. (Upstream is drifting toward file-based memory too — which validates direction without being the reason.)

**Why a quarry, not a break.** We keep pulling what's genuinely valuable — provider clients, new-model support, targeted fixes at the `llm_api` seam — and isolate our divergence to storage and interaction model. We stop pretending we are Letta; we keep benefiting from its parts.

**Bottom line.** The maintainer confirmed the base is legacy and the supported future is the architecture we reject. Project Technonomicon takes ownership of the substrate and the API our agents depend on, so upstream's abandonment cannot end them. It is continuity, made necessary by the people who built the thing we're leaving.
